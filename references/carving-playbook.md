# 文件雕刻实战手册

## 核心原则：先解析结构，再落盘

只按头尾签名截断（`FFD8` 到下一个 `FFD9`）会产生大量假文件。正确做法是按容器格式
**逐段解析到真实边界**，再用解码器/校验和验证，通过才写盘。

## 各格式要点

| 类型 | 起点签名 | 边界解析 | 验证 |
|---|---|---|---|
| JPEG | `FF D8 FF` | 走标记流：`FF01`/`FFD0-D7` 无长度段跳过；`FFDA`(SOS) 后进入熵编码，逐字节扫到 `FFD9`（忽略 `FF00` 填充与 `FFD0-D7` 重启标记） | PIL 全量 `load()` 解码 |
| PNG | `89 50 4E 47 0D 0A 1A 0A` | 走 chunk 链直到 `IEND`，每段 `len+4+type` 做 CRC32 校验 | CRC + PIL 解码 |
| GIF | `GIF87a`/`GIF89a` | 逻辑屏描述 → 全局色表 → 块链到 `0x3B` | PIL 解码 |
| WEBP | `RIFF....WEBP` | 头部 `size+8` | PIL 解码 |
| BMP | `BM` | 头部 `size` 字段 | PIL 解码 |
| MP4/3GP | `....ftyp` | 逐 box 递进（`size==1` 用 64 位，`size==0` 延伸到尾） | 必须同时见到 `moov` 与 `mdat`；有 `mdat` 无 `moov` 记为"可能不完整" |
| SQLite | `SQLite format 3\0` | `page_size × page_count`；`page_size==1` 表示 65536 | 以只读+immutable 打开，`sqlite_master` 非空 |
| ZIP/APK | `PK 03 04` | 走 local header 链；遇 `PK 01 02` 转中央目录找 `PK 05 06`(EOCD) | 有 data descriptor(flag bit 3) 时无法可靠跳链，放弃 |

## 必做的三件事

1. **跳过已雕刻区间内的签名**。App 缓存的缩略图、APK 内嵌图片会在大文件内部出现签名，
   导致重复与嵌套。实践中比较最近 3 条记录即可覆盖绝大多数情况。
2. **MD5 去重**。同一文件常被多处残留引用。
3. **渐进读取**。用小缓冲起步、按需倍增（`Reader` 类），避免为一个 4 KB 的 PNG 读 120 MB。

## 分类与命名

- JPEG 按"尺寸 ≥1200×900 或含相机 EXIF Make"归为相机原图，其余归为其他 JPEG（缓存/缩略图）。
- 相机原图阈值默认 300 KB，可用 `--min-photo` 调整。
- 输出按类型分目录，同时写 `carve_records.json`（含镜像偏移、MD5、EXIF、完整性标记），
  供后续与目录项配对使用。

## 期望值管理

- 明文残留区通常能救回数千个文件，但**绝大多数是 App 缓存与图标**（PNG/小 JPEG），
  用户真正想要的相机原图只占少数。先按尺寸和 EXIF 过滤，优先交付高价值文件。
- 视频体积大但命中率低：`moov` 在文件尾部的（非 faststart）常因尾部被覆写而缺失，
  表现为"有画面数据但不可播放"。
- 加密区的数据在任何雕刻方案下都拿不到，不要承诺。
